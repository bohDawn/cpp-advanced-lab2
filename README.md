## Суть проєкту

Програма досліджує швидкість операції **злиття двох відсортованих послідовностей** (`std::merge`, варіант 9) на різних обсягах даних і з різними режимами виконання. Порівнюються:

1. бібліотечний `std::merge` без політики виконання;
2. `std::merge` з політиками `execution::seq`, `execution::par` та `execution::par_unseq`;
3. **власний паралельний алгоритм**, який ділить роботу між `K` потоками (`std::thread`). Для кожного `K` вимірюється час, прискорення відносно `K = 1`, визначається найкраще `K` та його співвідношення до кількості апаратних потоків процесора (`std::thread::hardware_concurrency()`), а також `K`, після якого швидкість перестає зростати.

Додатково досліджується вплив **рівня оптимізації компілятора** (`-O0`, `-O1`, `-O2`, `-O3`). Усі вимірювання виконуються лише у режимі **Release**. Результат кожного режиму перевіряється порівнянням зі стандартним `std::merge`. Предикати для `merge` не досліджувались, бо за умовою завдання вони тут нерелевантні.

## Збірка та запуск

Проєкт використовує CMake (версії 3.10+) і вимагає компілятора з підтримкою **C++20**. Для `execution::par` та `execution::par_unseq` у GCC потрібна бібліотека **Intel TBB**.

### Залежності

**Windows (MSYS2, оболонка MINGW64):**
```bash
pacman -S mingw-w64-x86_64-gcc mingw-w64-x86_64-cmake mingw-w64-x86_64-ninja mingw-w64-x86_64-tbb
```

**Ubuntu/Debian:**
```bash
sudo apt install g++ cmake ninja-build libtbb-dev
```

### Швидкий запуск усіх рівнів оптимізації

З кореня проєкту (в MSYS2 MINGW64 або Linux):
```bash
./run_experiments.sh
```
Скрипт для кожного рівня `O0 … O3` видаляє стару папку збірки, конфігурує й збирає проєкт у Release, запускає програму та створює `results_O*.txt`.

### Збірка вручну (один рівень оптимізації)

```bash
cmake -S . -B build_O3 -G Ninja -DOPT_LEVEL=O3 -DCMAKE_BUILD_TYPE=Release
cmake --build build_O3
./build_O3/MergeExperiment
```

| Параметр | Значення |
|---|---|
| `-DOPT_LEVEL=` | `O0`, `O1`, `O2`, `O3` (за замовчуванням), `Ofast` |
| `-DCMAKE_BUILD_TYPE=` | **лише `Release`**. Інший тип збірки CMake відхиляє з повідомленням про помилку, бо в Debug прапорці `-O*` не застосовуються і результати були б хибними |
| `./MergeExperiment --regen` | перегенерувати вхідні файли |

> **Важливо.** Запускайте програму з кореня проєкту: вхідні файли `seq_*.txt` та вивід `results_<рівень>.txt` створюються в поточній теці.

## Використані засоби C++

* **`<execution>`:** політики `seq`, `par`, `par_unseq` для `std::merge`.
* **Потоки:** `std::thread` у власному алгоритмі, `std::thread::hardware_concurrency()` із захистом від нульового значення.
* **STL-алгоритми:** `std::merge`, `std::lower_bound`, `std::is_sorted`, `std::fill`, `std::sort`, `std::min_element`.
* **Генерація даних:** `<random>` (`std::mt19937`, `std::uniform_int_distribution`).
* **Шаблони та лямбди:** `measureMedianMs` приймає довільний викликаний об'єкт; усі вимірювані варіанти передаються лямбдами.
* **Час:** `std::chrono::steady_clock`, час у мс як `double`.
* **Структура коду:** окремі класи й файли для генерації, алгоритму, вимірювань; константи замість «магічних чисел»; `std::` у заголовках без `using namespace`.

## Алгоритм та прийняті рішення

### Власний паралельний `merge`

Перша послідовність `a` ділиться на `K` майже рівних частин за індексами. Для кожної межі `a[i]` у другій послідовності `b` знаходиться відповідна межа через `std::lower_bound`. Тому всі елементи пари відрізків `(a_i, b_i)` не більші за всі елементи наступної пари, і кожен потік **зливає свою пару відрізків одразу у свою ділянку вихідного масиву** (зсув = `a_begin + b_begin`). Фінального послідовного зливання немає, потоки не перетинаються за пам'яттю, тому синхронізація не потрібна, окрім `join`.

> Раніший (відкинутий) варіант розбивав обидві послідовності за індексами й після потоків послідовно зливав часткові результати. Ця послідовна частина з'їдала весь виграш від потоків, тому найкраще `K` майже завжди виходило 1–2.

### Методика вимірювань

* Годинник `steady_clock`; час у мілісекундах як `double`.
* Один прогрівальний запуск (холодний кеш, запуск пулу потоків TBB) і 15 повторів (5 для найбільшого набору). У таблицях **медіана**.
* Буфер результату виділяється поза вимірюваною ділянкою для всіх режимів, тож порівняння чесне.
* Кожен результат перевіряється порівнянням з еталонним `std::merge` (колонка `Correct`). Буфер перед кожним вимірюванням заповнюється нулями, щоб «порожній» алгоритм не пройшов перевірку.
* «Швидкість перестає зростати» = найменше `K`, чий час у межах 5% від найкращого.
* Діапазон `K`: `1 … 2·T`, а також `3·T` і `4·T` (де `T` = `hardware_concurrency`).

### Прийняті рішення

* **Одні й ті самі дані для всіх рівнів оптимізації.** Файли генеруються з фіксованим seed один раз і далі лише читаються.
* **Різні довжини послідовностей:** друга послідовність у 1.5 раза довша за першу; набори 10 000+15 000, 100 000+150 000, 1 000 000+1 500 000 і 5 000 000+7 500 000 елементів.
* **Захист від помилок:** якщо файли пошкоджені чи не відсортовані, програма завершується з повідомленням і підказкою про `--regen`.

## Формат даних і вивід програми

* **Вхідні файли:** текстові, цілі числа `1 … 100 000 000` через пробіл, відсортовані за зростанням, без заголовка. Імена: `seq_<N>_a.txt` та `seq_<N>_b.txt`.
* **Вивід:** для кожного набору таблиця бібліотечних режимів, таблиця власного алгоритму за `K` (час, прискорення відносно `K = 1`, коректність), найкраще `K`, його співвідношення до `T` і `K`, де зростання зупиняється. Наприкінці підсумкова таблиця `SUMMARY`. Той самий вивід записується у `results_<рівень>.txt`.

## Висновки

* **Найкраще `K` для великих даних дорівнює 9–11 (≈ 0.75–0.92 від числа апаратних потоків).** Швидкість перестає зростати біля `K ≈ T`; далі час або не змінюється, або погіршується, бо частина потоків мусить виконувати дві порції послідовно, а головний потік і ОС також потребують процесорного часу.
* **Масштабування обмежене пам'яттю:** прискорення `par` та власного алгоритму ≈ 7× на 6 ядрах / 12 потоках. Це більше за число ядер (SMT ховає затримки), але менше за 12×, бо на кожен елемент припадає лише одне порівняння та один запис.
* **На малих даних паралелізм не допомагає:** при 25 000 елементах `merge` займає ≈ 0.014 мс, а створення одного потоку коштує ≈ 0.1 мс, тому найкраще `K = 1`, а `par` навіть повільніший за звичайний `merge`.
* **Власний алгоритм порівнянний з `execution::par`** на найбільших даних (4.22 проти 4.08 мс при `-O3`). На середніх розмірах `par` швидший, бо TBB перевикористовує пул потоків, а власний код створює `K` потоків при кожному виклику.
* **`par_unseq` не кращий за `par`:** `merge` має залежності за даними й гілки, тому векторизація нічого не дає.
* **Оптимізація:** перехід від `-O0` до `-O1` дає найбільший виграш (2.8–3.8× для `merge`), бо без оптимізації шаблонні ітератори й обгортки політик не інлайняться (`seq` на `-O0` на 31% повільніший за звичайний `merge`). Рівні `-O1`, `-O2` і `-O3` практично не відрізняються (в межах шуму 5–10%), бо код упирається в пам'ять.
* **Похибка вимірювань:** повторні запуски відрізняються на 5–15% (на найменших `N` до 2×), тому в таблицях наведено результати одного повного запуску, збереженого у `results_O*.txt`.
